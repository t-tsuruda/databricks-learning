本ドキュメントは、Claude Code に対してアプリ開発を依頼するための実装指示書として使う。したがって、単なる提案ではなく、開発対象、要件、UI/UX、データ設計、実装順序、受け入れ基準まで含めた形で記述すること。

5. Webアプリケーションとして満たすべき一般的な要件（セキュリティ対策、レスポンシブデザイン、アクセシビリティ、パフォーマンス、学習進捗・履歴の保存、通知機能など）を整理してください。

7. MVPから段階的に機能を拡張していくための実装ロードマップ（フェーズ分け）を提示してください。
8. （重要）モチベーションが維持できるような仕組みにしてください。
9. ゆくゆくの拡張機能として、Snowflakeなどもサービスの学習サービスも入れ込んでいきたいです。

# ②以下詳細な、Claude Code向けの実装指示内容

## 1. プロダクトの目的と成功指標

- 目的：Databricksを「学びたいが、何から始めればよいか分からない初心者」が、基礎から応用まで段階的に学べる環境を提供する。
- 成功指標：
  - 初回ログイン後に3日以内に1つの学習モジュールを完了するユーザーが一定数いる
  - 1週間以内に2つ以上のコースを進めるユーザー比率が高い
  - 学習完了率が一定水準を超える
  - 1人で運用可能な範囲で継続可能な構成である
- 目標ユーザー：
  - データに興味があるが、SQLやPython、ETL、データ基盤に慣れていない人
  - 企業内でData EngineerやAnalystを目指す人
  - 自習でDatabricksを学びたいが、学習計画が立てにくい人
- 提供したい体験（プロダクトビジョン）
  - Databricksというツールを入り口として、AI時代において重要になるデータ基盤整備というスキルを身につけることで、学習者自身で新たなキャリアの足がけを作ること

## 2. スコープ定義（MVP/後続機能の明確化）

### MVP対象

- ユーザー認証（サインアップ/ログイン/ログアウト）
- 学習コース一覧と詳細ページ
- 学習進捗の保存
- 各モジュールに対する座学コンテンツとハンズオン課題
- 小テスト/確認問題
- 完了状態の表示と学習履歴
- ダッシュボード（進捗率、現在地、次の学習目標）

### 後続機能（Phase 2以降）

- コメント機能、Q&A機能
- 進捗や達成状況をSNS/共有可能にする機能
- 学習カレンダーやリマインド通知
- 管理者画面による講座更新・運用
- 質問生成AIアシスタント
- Databricks Notebook連携や実行コードの保存機能
- snowflakeなどの他サービスの学習

### 対象外

- シングルサインオン（SSO）
- マルチテナント構成
- 大規模同時利用に耐える高負荷設計
- ダウンロード販売型のコンテンツ配信

## 3. 画面構成とUI/UX要件

### 主要画面

- ランディングページ
- サインアップ/ログインページ
- ダッシュボード
- コース一覧
- コース詳細
- レッスン詳細
- 演習ページ
- 進捗管理ページ
- マイページ
- 管理者用ページ（将来）

### UI/UX原則

- 初学者向けに情報を最小限に整理し、次に何をすべきかが明確に見えること
- 1画面あたりの情報量は抑え、学習の心理的負担を減らすこと
- 各ステップに「学ぶ」「試す」「確認する」の3層を明示すること
- モチベーション維持のため、進捗率、完了数、達成バッジを視覚的に表示すること
- スマートフォンでも閲覧しやすいモバイルファースト設計を採用すること
- 学習の目的とキャリア価値が常に視界に入るようにすること

### モチベーション設計の追加要件

#### ① 冒頭・ステップごとのメッセージ設計

- 各学習開始時に、単なる説明ではなく「この学習で自分がどう変わるか」を明示する
- 例：
  - 「この章を終えると、データの整形と抽出の基礎を理解し、ETLの初歩を自分で設計できるようになります」
  - 「このレベルに到達すると、データ分析の下準備と簡単なパイプライン構築に参加できるようになります」
- セクションごとに「今の自分の立ち位置」と「次に到達できる姿」を結びつける
- 文章は「知識の説明」ではなく「キャリアへの進化の物語」として設計する
- 学習の導入時に、学ぶ意味とやる気を刺激する短いミッション文を表示する

#### ② キャリア視点の可視化

- ユーザーの学習進捗に応じて、現在のレベルを可視化する
- 例として以下のようなスキルレベルを表示する：
  - Level 1: データに関心を持っているが、基礎が弱い
  - Level 2: SQLとPythonで基本的な処理ができる
  - Level 3: ETLの基本設計とデータ整形ができる
  - Level 4: Databricksを使って簡単なデータパイプラインを運用できる
- ダッシュボードで次に習得できるスキルと、その先に就ける仕事を表示する
- 「今の自分がどこまでできるようになったか」と「市場でどんな仕事に向いているか」を一目で確認できるようにする
- 学習完了時に、その内容が「どのポジションで使えるか」を説明する

#### ③ 求人連動の可視化（MVPでは簡易版）

- 学習レベルに応じて、関連する求人職種や実務キーワードを表示する
- 例：
  - SQL基礎完了 → Data Analyst, Reporting Analyst, BI Support
  - ETL基礎完了 → Data Engineer Intern, Data Pipeline Assistant
  - Databricks基礎完了 → Junior Data Engineer, Analytics Engineer（初級）
- 求人表示は完全な求人一覧ではなく、参考用のサマリとキーワード提示とする
- 求人タイトルと関連スキルの対応関係を示し、学習と市場価値の接続を明確にする
- この機能は、学習へのモチベーションを持続させるための「未来の自分の姿」を見せるための重要機能と位置づける

#### ④ ダッシュボードの必須要件

- 現在の学習レベル
- これまでの完了数
- 次の学習目標
- これまでに身につけたスキル
- 獲得済みの達成項目
- 目指せる役割/仕事内容
- 直近の学習進捗のハイライト
- UI上で「あなたは今ここまで進んでいる」と一目で理解できる設計にする

### モチベーション維持のための代表的なメッセージ設計案

以下は例です。管理画面で制御できるようにしてください。

- 「最初の1歩は小さくても、あなたはすでにデータの入口に立っている」
- 「この単元を終えると、実務でよく使うデータ処理の基礎が身につく」
- 「今のあなたは、未経験者ではなく『学び始めた人』だ」
- 「次のステップに進むと、業務で使うスキルに近づく」
- 「あなたの成長は、求人での価値に直結している」

### 学習に対する心理的な設計思想

- 学習者が「自分はまだ足りない」と感じる瞬間に、次の一歩を具体的に示す
- 成長が見えるように、過去の学びを現在の自分の強みとして再認識できるようにする
- 途中で挫折しないように、学習の意味を「キャリアの進化」として説明する
- 勉強の成果を、単なる完了数ではなく「仕事でできるようになる可能性」に変換して伝える

## 5. ARCSモデルの設計反映

### Attention（注意）

- 最初の画面で「Databricksで何ができるのか」を明確に伝える
- 章タイトルと視覚情報を使って、学習の目的と価値を示す
- 学習途中で小さな達成感を与えるミニチャレンジを導入する

### Relevance（関連性）

- 各課題を「実務で使うデータ業務の一部」として説明する
- 例として「売上データの集計」「顧客分析」「ETLパイプライン」を使う
- 学習内容と将来の職務やキャリアでの価値を接続する

### Confidence（自信）

- 簡単な問題から段階的に難易度を上げる
- 「完了したら次へ進める」設計にし、挫折を減らす
- 解答のヒントやサポートを段階的に出す

### Satisfaction（満足感）

- 進捗率と達成バッジを表示する
- 学習完了時に簡単な振り返りを促す
- 実務課題に近い問題を解くことで達成感を与える

## 6. 認証基盤の設計方針

### 認証方式

- ID + Password を基本とする
- サインアップ機能は管理画面でON/OFFできるようにしてください。
- 可能ならパスワードのハッシュ化には bcrypt または Argon2 を採用する
- セッション管理はSecure CookieまたはJWTを使い分ける
- 2要素認証はMVPでは必須ではないが、将来検討対象とする

### 必須機能

- サインアップ
- ログイン/ログアウト
- パスワード再設定
- メール認証（MVPでは推奨）
- 退会処理
- ロール管理（一般ユーザー / 管理者）

### セキュリティ要件

- パスワードは平文保存しない
- CSRF対策を実装する
- XSS対策としてHTMLエスケープと適切な入力検証を徹底する
- SQLインジェクション対策としてORM/Prepared Statementを使う
- セッションの有効期限と自動失効を設定する

## 7. 一般的なWebアプリ要件

- セキュリティ：HTTPS、安全なCookie設定、CSP、入力バリデーション、レート制限
- レスポンシブデザイン：PC/タブレット/スマートフォンに対応
- アクセシビリティ：適切なカラーコントラスト、フォントサイズ、キーボード操作、aria属性の利用
- パフォーマンス：初期表示を軽くし、画像やコンテンツを最適化する
- 進捗管理：学習状態をDBに保存し、ユーザー毎に再開可能にする
- 通知：リマインドメールやダッシュボード通知の設計
- エラー処理：分かりやすいメッセージとログ記録
- 利用統計：GAやイベントログの導入を検討する

## 9. API設計とバックエンド要件

### バックエンド方針

- REST APIを採用し、フロントエンドと分離する
- 主要な責務はユーザー管理、学習進捗管理、コース情報提供である
- APIレスポンスはJSON形式とし、エラーコードを統一する

### 代表的なAPI

- GET /api/courses
- GET /api/courses/:id
- GET /api/courses/:id/lessons
- POST /api/auth/signup
- POST /api/auth/login
- POST /api/auth/logout
- POST /api/auth/reset-password
- GET /api/users/me
- GET /api/users/me/progress
- POST /api/lessons/:id/complete
- POST /api/quizzes/:id/submit

### バリデーション要件

- 入力値の形式チェック
- 不正入力や不正アクセスの遮断
- 例外時はユーザー向けに意味のあるエラーメッセージを返す

## 15. 受け入れ基準（Definition of Done）

- 一般ユーザーがサインアップしてログインできる
- コースを閲覧して、一部を完了状態にできる
- 学習進捗が保存され、再訪問時に復元される
- PCとスマートフォンで見やすいレイアウトになっている
- 管理者や開発者がデータベースや環境を把握できる
- 1人でも運用可能な実装として保守しやすい

## 16. Claude Codeへの最終指示

以下を守って開発を進めてください。

- 初学者体験を最優先にし、複雑な機能よりも実用的な体験を先に作る
- 機能数よりも完成度と使いやすさを優先する
- 無料枠で運用可能な設計にする
- 1人での開発を前提に、実装が簡潔で保守しやすい構成にする
- MVPでは必須機能に絞り、将来拡張を段階的に行う
- 学習の継続性を高める UX と進捗設計を常に重視する
- セキュリティとデータ保護は最低限の要件として実装する

## 17. 追加要件（初回リリース後の追記）

初回リリース後、実際の運用を見据えて以下の3点を追加要件とする。

### 17-1. 管理者向け管理画面

- 管理者（`users.is_admin = true`）でログインした場合にのみアクセスできる管理画面（`/admin` 以下）を設ける
- 一般ユーザーがアクセスした場合はダッシュボードなどへリダイレクトし、管理画面の存在自体が見えないようにする
- 管理画面で行える操作は以下の3領域とする
  - **アカウント管理**：ユーザー一覧の閲覧、管理者権限の付与/剥奪、ユーザーの削除
  - **コース/コンテンツ管理**：コースの作成・編集・削除・公開/非公開切り替え、レッスン（座学・ハンズオン・確認問題を含む）の作成・編集・削除、表示順の変更
  - **ダッシュボード構成管理**：サインアップ受付のON/OFF、モチベーションメッセージ（3章参照）の一覧編集
- 管理画面はシンプルな一覧・フォームベースのUIで良く、デザインの作り込みよりも「安全に・確実に運用できること」を優先する
- 管理者操作は、画面側だけでなくサーバー側（API/Server Action）でも権限チェックを行う（画面を直接叩かれても操作できないようにする）

### 17-2. Level 5：実務総合コース

- これまでのLevel 1〜4で学んだ内容（SQL、Python、データモデリング、Databricksの基礎、ETL、性能改善）を横断的に活用する、実務を想定した総合演習コースを追加する
- テーマは「オープンデータを使い、データ取得（Extract）→ 加工・格納（Transform/Load）→ BI可視化 までを一気通貫で行う、小さなデータ基盤構築プロジェクト」とする
- 扱うデータは、APIキーなどの登録が不要な公開オープンデータAPI（例：気象オープンデータAPI等）を利用し、学習者が実際に手を動かして取得できるようにする
- 構成は既存のレッスン標準構成（導入 → 座学 → 例題 → ハンズオン → 確認問題 → 次の行動提示）を踏襲し、「学ぶ・試す・確認する」の3層構造を維持する
- 最終レッスンでは、学習者がこれまでの学習内容を振り返り、「実務でどのポジションのどんな業務にこの経験が使えるか」を明示し、キャリア接続（3章のモチベーション設計）を締めくくる

### 17-3. 画面遷移のモーション

- ページ遷移時に、唐突な切り替えではなく、ふわっとした（フェード＋わずかな移動を伴う）遷移アニメーションを加える
- 初学者に「操作に反応している」という安心感を与え、ARCSモデルのSatisfaction（満足感）を補強する演出と位置づける
- `prefers-reduced-motion` を尊重し、アニメーションを抑えたい利用者には配慮する
- パフォーマンスへの影響を避けるため、軽量な実装（追加の重量級ライブラリに頼らない）とする

## 18. 追加要件（コンテンツ拡充とアプリ機能強化）

初回リリース後のレビューを踏まえ、「学習を完走すれば副業でデータエンジニアリング案件を獲得できるレベル」を目指し、以下を追加要件とする。

### 18-1. コンテンツのボリューム・深さ

- 各コースのレッスン数を大幅に増やし、1コースあたりの学習量を増強する
- ハンズオンは「手順を大まかに示す」のではなく、**番号付きの詳細なステップ**（実行するコマンド・期待される出力・次に確認すべきことを含む）に分解し、初学者が迷わず進められるようにする
- 各レッスンの「学ぶ」セクションには、**参考になる外部Webサイトへのリンク**（公式ドキュメント、信頼できる技術記事など）を1件以上添える
- Databricksそのものに関するコンテンツ（Lakehouse、Delta Lake、Unity Catalog、クラスタ／コンピュートの管理、Databricks CLIとRepos（Git連携）、Delta Live TablesとAuto Loader、Workflowsによるジョブオーケストレーション、コスト管理とクラスタポリシーなど）を大幅に拡充し、Databricksの実務利用に必要な知識を体系的にカバーする

### 18-2. アプリ機能強化（学習者向け）

- レッスンの「このレッスンを完了する」ボタンは、そのレッスンに含まれる確認問題に**すべて正解するまで非アクティブ**にする（クイズを解かなくても次に進めてしまう状態を解消する）。確認問題を持たないレッスンは従来どおり完了操作を許可する
- マイページから**パスワードを変更**できるようにする（現在のパスワードの確認を必須とする）
- ダッシュボードにおいて、学習者の現在のレベルに応じた**実際の求人情報**を外部の求人検索APIから取得して表示する（完全な求人一覧ではなく、参考情報としての表示とする）

### 18-3. アプリ機能強化（管理者向け）

- 管理画面での保存・削除・更新などの操作後、「保存しました」等の**明確な結果フィードバック**を画面に表示する
- アカウント管理画面から、**新規アカウントを作成**できるようにする
- コース/コンテンツ管理画面のハンズオン編集において、**スクリーンショットなどの画像を添付**できるようにする

## 19. 追加要件（コンテンツ運用の効率化とARCSモデルの深掘り）

18章の対応後も、「レッスンの作り直し・大量投入をもっと効率的に行いたい」「ARCSモデルを名目上でなく、実際の導線に落とし込みたい」という2点を追加要件とする。

### 19-1. レッスンのCSV一括インポート/エクスポート

- 管理画面のコース編集画面から、そのコースに属するレッスンを**CSVファイルで一括インポート**できるようにする
- インポートは既存レッスンと同じスラッグ（`slug`）であれば**上書き更新**、存在しないスラッグであれば**新規作成**として扱う（Upsert）
- 1レッスン1行とし、座学・具体例・ハンズオン・注意喚起（Attention）・関連性（Relevance）・できるようになったこと・関連する仕事・参考リンク・確認問題まで、レッスンを構成する全項目をCSVの列として表現する
- 生成AI（ChatGPTやClaudeなど）にCSVのフォーマットを渡し、まとめてレッスン内容を生成させてからインポートする、という運用を想定する。そのため、**列の意味が分かるひな形CSV（テンプレート）をダウンロードできる**ようにする
- 既存レッスンの内容を**CSVとしてエクスポート**できるようにし、「現状の内容を書き出す→AIや人手で編集する→再インポートする」という一新のサイクルを回せるようにする
- インポート時は行ごとに内容を検証し、不正な行があった場合はその行番号とエラー内容を管理者に分かりやすく表示する

### 19-2. ARCSモデルに沿ったレッスン導入部の再設計

- 各レッスン冒頭の導入文を、ARCSモデルの**Attention（注意喚起）**と**Relevance（関連性）**の2つの要素に明確に分割する
  - **Attention**：学習者の興味・好奇心を引く導入（「〜という経験はありませんか？」「実は〜」といった問いかけや意外性のある事実）
  - **Relevance**：学ぶ内容が学習者自身のゴール（副業でのデータエンジニアリング案件獲得、実務でのキャリア形成など）にどう繋がるかを明示する文章
- レッスン画面では、この2つを分けて表示し、学習者が「気になる→自分に関係がある→だから学ぶ」という流れを体感できるようにする
- 管理画面のレッスン編集フォームでも、AttentionとRelevanceをそれぞれ独立した入力欄として編集できるようにする
- 19-1のCSVインポートの列にもAttention/Relevanceを含め、生成AIでレッスンを作成する際にもARCSモデルに沿った内容を意識して生成できるようにする

# 最終的な提案まとめ

Databricks学習アプリは、単なる教材配信サイトではなく「初学者が順応しながら段階的に上達できる学習プラットフォーム」として設計するべきです。特に重要なのは、学習の進め方・モチベーション維持・進捗の可視化・実践課題の組み合わせです。

本アプリのコア価値は、

1. 初学者が何から学べばよいか迷わない導線を提供する
2. 学習の進捗が明確に見える
3. 理論と実践がセットになっている
4. Databricksで実際に手を動かせる
5. 継続的に学べる仕組みがある

という5点にあります。

この方針に基づいて開発を進めると、単なる資料集ではなく、実際に学習を続けられるアプリとして成立します。Claude Code には、上記の観点を踏まえたうえで、最初にMVPを1本完成させ、次に拡張機能を順に追加する実装フローで開発を進めてください。
